# Building PDM: a from-scratch multi-connection download manager

> 这是一篇可发布到博客/社区的技术文章草稿。项目仓库：
> <https://github.com/earllee-study/personal-download-manager>

## 为什么写一个下载管理器

浏览器自带的下载器通常只做单连接顺序下载。面对高延迟、单连接限速或大文件时，多连接分段下载往往能显著缩短时间；但分段、续传、校验、动态拆分、失败回退这些细节并不简单。

PDM（Personal Download Manager）是一个从零实现的 Windows 桌面下载管理器，目标不是做一个商业产品，而是把多连接下载、HLS/DASH、浏览器集成和 MSE 捕获这些机制做成可测试、可复现的开源实现。

## 核心流程

一次典型下载分为四步：

1. **探测**：用 `GET Range: bytes=0-0` 获取最终 URL、文件大小、是否支持 Range，以及 ETag / Last-Modified。
2. **分段**：按大小和连接数切分字节区间，每个 worker 负责一段。
3. **并发写入**：所有 worker 按偏移写入同一个预分配文件；没有最后的“合并临时分片”步骤。
4. **收尾**：校验 SHA-256，原子改名，写入 journal。

续传依赖原子 JSON journal：每个分段的游标在字节落盘后更新。进程崩溃最多导致重新下载，不会跳过数据。

## 动态分段

固定分段有一个问题：如果某个连接提前完成，其他连接仍在慢慢跑，空闲连接就浪费了。

PDM 的策略是：

- worker 完成后，找到剩余工作量最大的活动分段；
- 从该分段当前游标处一分为二；
- 把后半段交给空闲 worker；
- 切分点被限制在受害分段的实时游标内，保证没有字节被下载两次。

本地基准中，4 个连接里 1 个快、3 个慢时，动态分段把 16 MiB 下载从 2.08s 降到 1.63s，分段数从 4 变成 7。

## 一致性校验

分段下载最怕服务器内容在下载过程中变化。PDM 使用：

- `Accept-Encoding: identity`，避免压缩让字节偏移失效；
- ETag / Last-Modified + `If-Range`；
- 完成后 SHA-256；
- 内容变化时明确失败，而不是拼出一个损坏文件。

## HLS / DASH

除了普通 HTTP，PDM 还实现了：

- HLS VOD：master 播放列表、相对路径、`EXT-X-BYTERANGE`、`EXT-X-MAP`、标准 AES-128 解密；
- DASH：`SegmentTemplate`、`SegmentTimeline`、`SegmentList`、单文件 Representation、多 Period、SegmentBase + SIDX；
- 双轨下载与可选 ffmpeg `-c copy` 合并。

直播、DRM、SAMPLE-AES 和非 identity KEYFORMAT 会明确拒绝，不做绕过。

## 浏览器与 MSE

浏览器扩展通过 Native Messaging 把链接交给桌面端。除了普通链接，扩展还会扫描页面 DOM、内联脚本、iframe 和开放 shadow DOM 中的媒体地址。

MSE/blob 捕获是实验功能：在页面 MAIN world 中 hook `MediaSource.addSourceBuffer` / `SourceBuffer.appendBuffer`，按 SourceBuffer 分轨写入未加密 fMP4/WebM。捕获结束后可以作为“已捕获”任务进入 GUI 队列，并可选 ffmpeg 合并。

## 测试与可复现基准

项目目前有 393 项自动化测试，覆盖：

- 本地 HTTP/1.1、TLS+h2、QUIC 服务器；
- FTP/FTPS/SFTP 服务器；
- 断流、重试、续传、Range 变化；
- GUI offscreen 测试；
- 打包与发布脚本。

性能结论都要求有可复现的本地基准，而不是只贴一个公网数字。
